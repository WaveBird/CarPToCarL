## 3. B. 失败点归类

### 3.1 `read failed, socket might closed or timeout, read ret: -1`（8 次，全部出站）

**上下文**：全部是 **App 主动出站** `createRfcommSocketToServiceRecord(…caff)` 到已配对设备后**立即**失败，耗时 0.08–0.64 秒：

| 时刻 | 目标 | 行号 | 同轮前置动作 |
|---|---|---|---|
| 00:26:33.021 | BMW 71280 | L94 | 先断了车机 HFP（L89） |
| 00:26:56.453 | BMW 71280 | L142 | — |
| 00:27:41.487 | **WF-SP700N** | L176 | 目标已拉黑（L170） |
| 00:28:33.412 | **WF-SP700N** | L195 | — |
| 00:29:24.072 | **WF-SP700N** | L208 | — |
| 00:30:29.727 | **WF-SP700N** | L226 | — |
| 00:32:17.829 | BMW 71280 | L472 | 车机 8 秒前刚关链路 |
| 00:33:06.405 | BMW 71280 | L798 | 车机 1 秒前刚关链路 |

**判断**：
- 报错文案是 Android 在 `BluetoothSocket.connect()` 失败时给出的通用句（`read failed, socket might closed or timeout, read ret: -1` 来自底层 `read()` 返回 -1），**它不是 15 秒超时**——本次 8 次全部在 **0.08–0.64 秒**内返回，说明对端（车机）在 SDP 记录存在但 RFCOMM 端**未开窗**时立刻拒绝。
- 这是 **MGU-55-J 的既定行为**：它只在「无线 CarPlay 窗口」里接受 `…caff` 入站；本次全部 6 次成功建链都是它自己连进来的（§2.3 的 I1–I5）。
- 因此「16 秒后再拨」这条策略在这台车上**没有一次奏效**，而它的副作用（先断 HFP/A2DP，L89/L90/L671-676 代码路径）直接制造了 8 次断开与车机的 8 次反向重连。
- 另注：`L704-L711` 的分支逻辑对「SDP 里查不到服务」和「连得上但被拒」给了不同提示；本次报的全是 `read failed`，走的是后者，于是打出了「车机未就绪或不在无线配对窗口」——这个判断对**车机**成立，对**耳机**（WF-SP700N）就是胡说。

### 3.2 `SDP 明确不含 iAP2 服务` —— 事实对，结论错，且不可逆

**日志原文**：`L170 @00:27:31.203 BT-C: 跳过「BMW 71280」（SDP 明确不含 iAP2 服务——非 CarPlay 设备，保持其音频连接）`

**SDP 查询结果到底是什么**：日志**没有打印** SDP 返回的 UUID 列表或记录数——只给了「MISSING」这个三态结论（`Iap2Service.MISSING`）。所以「SDP 结果」在日志层面**未体现**，只能从结论反推：那一刻 `…caff`（iAP2 服务）的 UUID 不在车机的 SDP 记录里。

**这条判断合理吗**：一半合理、一半是硬错。
- 合理处：`awaitIap2Service()` 的存在本身是对的（避免把耳机/手表全拨一遍），代码注释（`Iap2BluetoothClient.kt` L610-618）也解释了动机。
- 硬错处：把「此刻 SDP 里没有」当成「**这台设备不是 CarPlay 设备**」，并且**缓存了一辈子**。`skippedNoService` 只在整个 `connect()` 启动时清一次（`Iap2BluetoothClient.kt` L202 定义、L394 `skippedNoService.clear()`、L624/L647 写入、L899 `if (skippedNoService.contains(device.address)) return false`）。本次 00:26:37 启动后，BMW 71280 在 00:27:31 被写入黑名单，**此后直到 00:31:26 用户手动停止都没有再被拨过一次**——而同一台设备在 5 分钟后就成功建了 6 次会话。这就是自我实现的失败。
- 更要命的是**时机**：MGU-55-J 的 `…caff` 是在车机自己准备开无线窗口时才广播的。我们在它没开窗的时候去查 SDP，必然查不到。

**同类第二例**：`L182 @00:28:02.085 跳过「BMW 47180」（SDP 未给出结论、直连 …caff 也失败）`——`BMW 47180` 显然是同一台车机的另一条配对记录（同一辆车的第二个 HFP 身份/另一台 BMW）。它被按「非 CarPlay 设备」处理，同样永久拉黑。

### 3.3 `连接 WF-SP700N 失败` —— 是 bug，而且是两个叠加的 bug

**为什么 App 会去连一个耳机**：`L163 @00:27:09.172` 目标连续 2 轮连不上 → `BtSessionGate.targetSoftFallback = true`（代码 L726-L732），候选集从「只有 BMW 71280」变成「所有已配对且未被排除的设备」（L859-L899）。**排除**依赖 `keepAsSoftCandidate()` → `looksLikePersonalAudio()`（`PersonalAudioClassifier.kt`）。

**为什么 WF-SP700N 没被排除**：
1. `PersonalAudioClassifier.NAME_KEYWORDS`（`PersonalAudioClassifier.kt` L34-L38）只有 `buds / airpods / freebuds / headphone / headset / earphone / earbuds / speaker / soundbar / 耳机 / 耳塞 / 音箱 / 音响 / 降噪`。**`WF-SP700N` 一个都不含**（`sp`、`wf-` 都不在表里）。
2. 该类的注释（L1-L12）自己写明：Android 16 上 `bluetoothClass` 经常拿不到，只能靠名字兜底。本次设备是 Android 17 (SDK 37)（L5）。名字兜底失效 = 判不出来 = 当成可能的车机。
3. 副产品更糟：`Iap2BluetoothClient.kt` L671-L676，若 `looksLikePersonalAudio` 为 false，`tryConnect` 失败后会先 `BtProfiles.disconnect()` **断掉它的 A2DP/HFP** 再试。日志里没有出现 `BT-C: WF-SP700N 处于蓝牙已连接状态——已断开重试`（该行受 `PROFILE_LOG_THROTTLE_MILLIS` 节流），所以**不能证明**这次真把耳机音频掐了，但代码路径就在那儿。用户当时若戴着耳机听歌，观感就是「蓝牙一直断」。

**它有没有可能把耳机误当车机**：会，而且这次就是这么发生的——`L176/L195/L208/L226` 四次 `连接 WF-SP700N 失败`，提示语还写着「车机未就绪或不在无线配对窗口」，整整 3 分钟（00:27:41–00:30:29）的"车机重试"其实全打在耳机上。

### 4.3 `WiFi: 尚未拿到热点密码（车机还没下发 0x4301）` 这条

**`0x4301` = `CarPlayStartSession`**（日志自己给的译名，`L322`：`可选消息声明：StartHID(0x6800)=会发 CarPlayStartSession(0x4301)=不发`）。

### 4.4 成功那次（00:33:14.234 起）WiFi 是怎么连上的，和失败时有什么不同

- `BT-C` 在 00:33:40.426 的「被动等待 15 秒」（L1351）之后**再无任何 BT-C 日志**——主动拨号循环事实上停住了（因为 `BtSessionGate.sessionActive` 为真时走 `sleepQuietly(2000)` 静默分支，代码 L561-L571）。
- 所以 00:33:43 之后到日志结束（70 秒）是**唯一一段完全稳定**的时间。倒车期间没有触发任何重连。

> 反过来说，这也意味着：**一旦推流建立，App 就再也不管 BT 控制链路了**。00:33:39.451 车机主动断开 RFCOMM 时 App 判断「iAP2 已迁到 WiFi 隧道」，但隧道链路一直卡在 `NEGOTIATING`（§5.2），没人发现这件事。

### 7.2 修复清单（按优先级）

#### P0-1　把「主动拨号」降级为兜底，先给车机建链窗口
- **现象**：8 分钟里主动拨号 0 成功，却制造了 8 次断开；用户每次重试都在打空。
- **日志证据**：L94、L142、L176、L195、L208、L226、L472、L798（全失败）vs L293、L474、L632、L800、L1001、L1353（全成功且全是车机发起）。
- **代码位置**：`app/src/main/java/io/github/shaonialife/carptocar/bt/Iap2BluetoothClient.kt` `connect()` 主循环 L514-L787；`awaitCarInitiated()` L791-L830（已存在但只在 `PASSIVE_FALLBACK_ROUNDS=2` 次 SDP 失败后才进）。
- **建议改法**：默认进入 `connect()` 时先走 `awaitCarInitiated(30s)`（被动窗口），窗口内车机没连入再拨；`PASSIVE_FALLBACK_ROUNDS` 从 2 降到 0（即"第一次失败就切被动"）。对已记录「曾成功入站」的车机（`BtSessionGate` 里有痕迹）应**直接跳过主动拨号**。

#### P0-2　绝不把「用户显式选定的目标」写进 `skippedNoService`，并给 SDP 结论加 TTL
- **现象**：真正的车机在 00:27:31 被自己的闸门判死，此后 3 分钟全打在耳机上。
- **日志证据**：L170（BMW 71280 被跳过后再无一次拨号记录）；对比 L176/195/208/226 全是 WF-SP700N。
- **代码位置**：`Iap2BluetoothClient.kt` L610-L628（`gate == Iap2Service.MISSING` 分支）、L202 `skippedNoService`、L394 清空、L899 判空。
- **建议改法**：① `targetProvider() != null` 且 `device.address == target.address` 时**永不**写黑名单（SDP 缺失只记录、不跳过）；② 非目标设备的黑名单加 TTL（30–60s）；③ 日志把 SDP 的原始 UUID 列表打出来（现在是空的，只有"MISSING"这个结论）。

#### P0-3　会话换代时必须取消所有挂起定时器（0x4301 8s 窗口）
- **现象**：00:32:45.983 把一个已经拿到 0x5703 的活会话判死，还打印了错误原因。
- **日志证据**：L629（00:32:37.982 装填）→ L632（00:32:39.571 新链路建链）→ L747（00:32:42.167 0x5703 到手）→ L777/L778（00:32:45.982 引爆，声称"既没回 0x4301、也没有 0x5703"）。
- **代码位置**：`app/src/main/java/io/github/shaonialife/carptocar/iap2/Iap2SenderSession.kt`（`0x4301 窗口`、L170-L215 的"等待态/已拿到 0x4301"标志）、`SessionController.kt` 的会话生命周期。
- **建议改法**：① 定时器持有 `generation`/会话 id，引爆前校验；② 链路关闭（`LINK closed`）时统一 `cancelPendingTimers()`；③ 收到 0x5703 即视为拿到 AP，立刻取消 0x4301 窗口；④ 失败文案改成实际拿到的消息列表。

#### P0-4　WiFi 入网不跟随 BT 会话生灭；复用判定不依赖 SSID
- **现象**：join 前两次都被"车机链路已断开"取消；而手机一直在 172.16.222.107。
- **日志证据**：L441→L453→L465（join#1 被取消）、L773→L782→L796（join#2 被取消）；对比 L63/L113/L271（wlan0/172.16.222.107 全程在）、L1157/L1481（本机 172.16.222.107）；判定行 L439/L445/L772/L940/L947。
- **代码位置**：`net/CarNetworkReadiness.kt` L85-L138（`ABSENT` 分支 L133-L138）、`net/NetworkReusePolicy.kt` L56-L65、`net/WifiCarPlayConnector.kt` `joinCarPlayNetwork()`（L209 起、`onUnavailable` L293/L456/`Unavailable` L314/L329/L343）、`SessionController.kt` L261/L281。
- **建议改法**：① 复用判定改用「已绑定网络 + 有地址 + 网关/对端可达」而不是 SSID 相等（位置服务关闭时应走 `expected == null` 的 READY 分支，现在走成了 ABSENT）；② join 用一个独立作用域的 Job，BT 断链只记录不 cancel；③ join 请求在 `onUnavailable` 后不要等 5s 才重试（本次 L942→L947 白等 5 秒），可立即重试一次再退避。

#### P0-5　让隧道 iAP2 链路在推流会话里真正升到 NORMAL，并让 0x5001 走隧道
- **现象**：车机首页无音乐信息。
- **日志证据**：L1591（00:33:43.993 NEGOTIATING，此后无 NORMAL）；L1678（0x5001 未发出，`mib3Identified=false tunnelIdentified=false`）；L1682/1735/1756（仍从 BT 发出）；0x5000 只有 L584。
- **代码位置**：`app/src/main/java/io/github/shaonialife/carptocar/airplay/VirtualIap2Link.kt`（`0x5001 未发出——iAP2 控制面带内会话尚未识别` 这条日志的来源）、状态机 NEGOTIATING→NORMAL 的迁移条件（对照 I4 的 L1260→L1262 是成功的）。
- **建议改法**：① 把「NEGOTIATING 超时」变成一条显式告警日志（现在是静默）；② 对比 I4（成功）与 I5（卡住）的差异——I4 的隧道 0x1D01 是 31 项清单、I5 只有 BT 侧清单（L1375 是 16 项），说明 **I5 的隧道识别握手可能根本没开始或没收到 0x1D01**；③ 0x5001 优先走已识别链路，BT 只做兜底，且**不要**在"未发出"之后再发一遍（L1678 与 L1682 自相矛盾）。

#### P1-6　耳机判定加严：候选必须真的提供 `…caff`
- **现象**：索尼 WF-SP700N 被连拨 4 次，还收到"车机未就绪"的错误提示。
- **日志证据**：L176/195/208/226。
- **代码位置**：`bt/PersonalAudioClassifier.kt` L34-L38 `NAME_KEYWORDS`；`Iap2BluetoothClient.kt` L859-L899 `candidateDevices()` / `keepAsSoftCandidate`、L671-L676（断音频路径）。
- **建议改法**：① 软回退的候选也强制过 SDP 闸门（`awaitIap2Service()` 返回 HAS 才拨），代价是多一次 SDP 查询，收益是彻底不碰耳机；② 名字表补 `wf-`/`wh-`/`sp-` 等型号前缀（或改成"含数字型号 + 无 CarPlay 关键词"的启发式）；③ `looksLikePersonalAudio` 判不出时，日志要明确写「无法判定是否音频设备」而不是伪装成车机。

#### P1-7　重试提示文案用真实退避值
- **现象**：每句都写「16 秒后重试」，实际 16/20/24/30/45/60 都在用。
- **日志证据**：L94/142/176/195/208/226 的文案 vs L183（24s）/L198（30s）/L211（45s）/L229（60s）；实测到下次失败的间隔 31.3s/40.4s/55.4s。
- **代码位置**：`Iap2BluetoothClient.kt` L704-L712（`RETRY_DELAY_MILLIS / 1000` 硬编码在字符串里）。
- **建议改法**：把 `backoffMillis(failStreak)` 提前算出来，同一个值既用于 `sleepBackoff` 也用于日志。

#### P1-8　统一个「断链后冷却」常量，并对非手动断链生效
- **现象**：16s 与 18s 两套语义；三次车机侧断链完全没冷却，1–7 秒后就带着残留状态重开。
- **日志证据**：L121（18s 生效，实测 19.00s）；L460/L790/L992（`bt socket closed`，无冷却，车机 7.4s/1.0s/0.9s 后重连）；`RETRY_DELAY_MILLIS=16_000`（L72）vs `REACTIVATE_COOLDOWN_MILLIS=18_000`（L1274）。
- **代码位置**：`Iap2BluetoothClient.kt` L72 / L86 / L525-L535 / L1274；`BtSessionGate`（L1249-L1290）。
- **建议改法**：删掉 16s 这个常量，只留 18s，并把判断从 `sinceManualStop()` 改成 `sinceAnySessionEnd()`；进入冷却前先 `cancelPendingTimers()` + 清 join 状态。

#### P2-9　0x6800 StartHID 缺失的兜底
- **现象**：方向盘切歌永远不工作。
- **日志证据**：0x6800 仅 L589（短命会话）；L1599、L1650/L1667。
- **代码位置**：`Iap2SenderSession.kt` 的 HID 处理；`EVENT: HID 体检` 来源模块。
- **建议改法**：代码里 L1223 自己已经给出结论（"只能靠 0x6800/0x6802"）——需要在车机不发 StartHID 时**主动**发 0x6802 前先尝试 0x6800 探测，或退回 AVRCP 绝对音量/播放命令；至少要在 UI 上明确"本车不支持方向盘切歌"，别让用户以为是 App 坏了。

#### P2-10　修正三处错误归因文案
- **现象**：给排障者的错误方向。
- **日志证据**：L216（`尚未拿到热点密码（车机还没下发 0x4301）`）、L176/195/208/226（`车机未就绪` 但对象是耳机）、L778（`既没回 0x4301、也没有 0x5703` 但 0x5703 已在 L747 到手）。
- **代码位置**：WiFi 提示（`SessionController.kt` / `WifiCarPlayConnector.kt`）、`Iap2BluetoothClient.kt` L704-L712、`Iap2SenderSession.kt` 的失败构造处。
- **建议改法**：文案里禁止出现"0x4301"作为密码来源；失败文案必须附上本轮实际收到的消息 id 列表。

#### P2-11　「不在已配对列表」要复查再下结论
- **现象**：00:31:45 判定目标未配对 → 无候选 → 空转 6 秒；6 秒后车机就成功连入了。
- **日志证据**：L261 / L287 / L288 vs L293。
- **代码位置**：`Iap2BluetoothClient.kt` L829-L860（`candidateDevices()`）、`MainActivity.kt` PREFLIGHT 的配对检查。
- **建议改法**：用 `BluetoothDevice.getBondState()` 逐设备复查（`bondedDevices` 快照在配置文件反复断开后可能瞬时不全），并对目标设备做一次 `fetchUuidsWithSdp()` 重试；两次都确认未配对才报"未配对"。

#### P2-12　主屏"永久归属"要在每次 requestUI 后复核
- **现象**：车机 00:34:33 拿走永久主屏后，App 连做 3 次「让出→拿回」并全部自报成功，但用户看到的是进不去。
- **日志证据**：L1822–L1825（主屏=车机/永久=车机）vs L1830–L1836、L1865–L1868、L1878–L1881。
- **代码位置**：`airplay/` 的 modesChanged / MODE 模块（日志标签 `MODE:`、`RESOURCE:`）、`0x34:34.474 主屏归还手机…已补关键帧秒切`。
- **建议改法**：① requestUI 成功后检查复述里的 `永久` 字段，若仍是 `车机` 则不要打"成功"，改为"暂时占用，永久归属仍在车机"；② 对同一 requestUI 做 3 秒内的去重（本次 19 秒内 3 次跳变，明显在打转）；③ 每次跳变之间加最小间隔，避免车机侧反复重绘。
