# 最后一次采集：一次性收口全部遗留未知（2026-11-25）

> 目标：**一次上车**关闭所有剩余未知，不再出现「测一点修一点」的循环。

## 一、为什么已有日志修掉了能修的，还剩一件事

已修复的缺陷，根因全部来自已有日志，不是猜测：

| 缺陷 | 日志证据 | 修复版本 |
|---|---|---|
| 重试 5 分钟全败 | 主动拨 0 成/入站 6 成、SDP 误拉黑 3 分钟、16s<18s | 1.2.106 |
| 倒车后进不去 | 19:35:39-50 fighting→车机拆链完整序列 | 1.2.107 |
| 已保存目标仍轮询 | 每轮遍历+SDP 白查 | 1.2.108 |
| 死链陪跑 join / SSID 误判重入网 | 22-26s 短命会话、全程在热点却判无网络 | 1.2.109 |

「待实车验证」指的是同一件窄事：**车机对我们新行为（不对抗、直达拨号、跳过 join）的反应**。旧日志里不存在这个反应，因为这些行为此前从未发生过。这不是「修复没把握」，而是「车机的接受度只能由车机自己回答」。

## 二、唯一真正的数据缺口

**iPhone 对车机资源仲裁消息（changeModes take-permanent / requestUI）的应答帧。**

为什么至今没有：
1. iPhone oslog 里 `modesChanged`/`requestUI` 命中 = 0（os_log `<private>` 脱敏）
2. WiFi pcap 会话阶段 ChaCha20 加密，只有配对阶段明文
3. 采集当晚 iPhone **没有做倒车流程**——它的资源仲裁帧从未发生过

为什么重要：1.2.107 的 fighting 防护按「车机消息语义 + 不对抗」推断。iPhone 收到车机 take-permanent 后到底**发不发帧、发什么 transferType**，是唯一能一锤定音的 ground truth。拿到它，主屏仲裁逻辑就从「推断对齐」变成「逐字节对齐」。

## 三、一次采集的完整清单

**设备**：iPhone（USB 连 Mac，frida hook `accessoryd`/`iapd` 的 iAP2 出入口——管线已验证可用）+ 17PM（1.2.109 已装，App 日志判据已埋好）。

**操作**（每步间隔 3~5 秒）：
1. 上电 → 等自动连接 → 进 CarPlay → 播歌 15s
2. **挂倒挡 → 等 5s → 回 CarPlay**（不手动断连！）← 关键段
3. 车机上断开 iPhone → 等车机自动重连 → 进 CarPlay
4. 播歌 10s → 结束

**这一趟同时回答的问题**：

| 问题 | 判据（哪台设备的哪个数据） |
|---|---|
| iPhone 倒车后对 take-permanent 发什么帧 | iPhone frida iAP2 出入口捕获 |
| fighting 防护后车机还拆不拆链 | 17PM 日志：倒车段无 `让出→拿回` 风暴、无 control EOF |
| 倒车后能否直接回 CarPlay | 体感 + 17PM 日志 `requestUI` 后复述归属=手机 |
| 直达拨号是否生效 | 17PM 日志 `已保存目标直达拨号` |
| 死链预检/网关兜底是否生效 | 17PM 日志 `跳过本轮 join` / `网关判定已在车机热点` |
| 首页歌名 | 车机屏幕 + 17PM 日志 NowPlaying 推送记录 |

**降级方案**：若 iPhone 帧仍抓不到（hook 层打偏），仅凭 17PM 日志也能间接判定——fighting 消除后车机不再 take-permanent 收回、不再 EOF，即证明「不对抗」策略被车机接受；iPhone 逐字节对齐降级为后续优化项。
